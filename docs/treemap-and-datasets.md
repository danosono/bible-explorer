# Overview treemap sizing & topic/concordance datasets

Reference notes for the Overview ("Bible View") treemap layout and the four
topic/reference datasets behind the Dataset dropdown. Written so future work
on book sizing, pin-line rendering, or new datasets doesn't have to
rediscover this from scratch.

## Overview treemap sizing (`js/app.js`)

### Data source: character counts
- `data/book-character-counts.json` — `{ metadata: {...}, books: { GEN: 182159, ..., REV: ... } }`,
  one entry per book, summed from `verse.text.length` across every chapter/verse
  in `data/bible.json`.
- Generated by `scripts/compute-character-counts.js` (run once, output committed).
- `buildItems()` (~line 1109) sets each item's `value` to
  `characterCounts[book.id]` (falling back to `verseCount`, then `1`). The
  synthetic `SEPARATOR` item ("0 AD", inserted after MAL) has a fixed
  `value: 100`.

### Layout: `enforceAspectRatios(items, width, height)` (~line 1209)
14 fixed-width columns; each item's height is derived from its `value`. Two
problems showed up once real character counts were used directly:

- Character counts span **~138x** (Jeremiah 207,838 vs. 2 John 1,502), so a
  linear value→height mapping plus the `minHeight = 110` floor (needed to fit
  3 pin lines) caused ~73% of cards to clamp to the same 110px floor.
- The old fixed `booksPerCol = ceil(items.length / 14)` slice assigned books
  to columns in groups of 5 regardless of actual content height, so a column
  could have a couple hundred px of empty space below its last book while the
  next book was forced into a new column (e.g. 1 Kings vs. 2 Samuel).

Current approach:
1. **Sub-linear weight** — `item.sizeWeight = Math.pow(item.value, 0.3)`.
   Compresses the 138x range to ~4.4x so short books differentiate from each
   other above the floor instead of all clamping identically. (0.3 was chosen
   empirically via `scripts/verify-treemap-packing.js` - sqrt (0.5) only got
   the floor count down to ~54% at HD; 0.3 gets it to ~45% at HD and ~6% at
   4K while still giving the largest books a clearly taller ~2x silhouette.)
2. **Greedy shelf packing** (`packColumns(unitHeight)`) — walk items in
   canonical order (Genesis → Revelation, with the "0 AD" separator after
   Malachi), accumulating into the current column until the next item would
   overflow `height`, then start a new column (capped at 14). Preserves
   reading order while letting columns absorb however many books fit.
3. **Binary search for `unitHeight`** — 25 iterations searching for the
   smallest `unitHeight` where `packColumns` uses all 14 columns (too small
   leaves trailing columns empty, too large overflows the last column).
4. **`scaleFactor` squeeze** — if the densest resulting column still slightly
   overflows `height` after the binary search, scale all heights down
   uniformly to fit.
5. **Per-column `fillFactor` stretch** — after `scaleFactor`, any column whose
   total height is *less* than `height` (commonly the last column or other
   columns near the start of the search range that ended up sparser) is
   stretched uniformly so it sums to exactly `height`. This eliminates empty
   space below the last card in a column (e.g. previously ~345px below
   Revelation at HD) and gives every card a bit more room for pin lines.

`item.value` (raw character count) is left untouched; `item.sizeWeight` is a
layout-only derived field. This is resolution-independent (works for both HD
and 4K, since `height` is the actual rendered viewport height passed in by the
caller).

Dead code, not used by the final layout: `normalizeAreas`, `worst`,
`layoutRow`, `squarify` (~lines 1136-1207, a squarified-treemap algorithm from
an earlier approach). The Book View chapter treemap is a separate code path
(verse-count based) and is out of scope for all of the above.

`scripts/verify-treemap-packing.js` is a standalone (not runtime) Node script
that re-implements this algorithm against the real
`data/book-character-counts.json` and prints the resulting column packing,
floor-clamped item count, and 1 Kings/2 Samuel placement for representative
HD/4K dimensions - useful for re-tuning the exponent or `minHeight` without a
browser.

## Pin-line rendering

Topic/word references render as small horizontal "pin lines" inside each
book card, positioned by vertical percentage within the book.

- **Overview**: `renderTreemap` (~line 1330-1460+).
- **Book View**: `renderBookView` has an equivalent block (~line 1798-1845)
  for chapter cards — same logic, mirrored.

Mechanics:
- For each reference, `getAbsoluteVerseIndex(bookId, chapter, verse)` gives an
  absolute verse index within the book; consecutive absolute-verse indices are
  merged into ranges (no spatial/positional deduplication beyond this).
- `.pin-lines` is a `flex-wrap` flow container (4 quarter-width "columns" per
  row). Each range's `.pin-line` gets an inline `flexBasis` from
  `getPinLineWidthPercent(verseCount)` (~line 283): 1 verse → 25%, 2-3 → 50%,
  4-6 → 75%, 7+ → 100%. Ranges render in book/chapter reading order (DOM order
  = `verseRanges` order, already sorted by absolute verse position), so pins
  flow left-to-right, top-to-bottom like text.
- Ranges >10 verses additionally get `.pin-line-wrapped` (thinner, brighter;
  combined with the 100% flexBasis from the tier above).
- `.pin-line--ot` / `--nt` / `--mixed` color the line by whether its
  reference(s) fall in the OT, NT, or both.

This replaced an earlier absolute-positioned layout (`top: <percentage>%`,
continuous width formula `Math.min(20 + (verseCount-1)*8, 100)`) that
left-pinned every range to its own full-width vertical slot regardless of
verse count - wasting most of the row for the common single-verse case and
giving high-frequency words no way to show more than one pin per row.

### Overlap handling
With the flex-wrap layout, pins no longer overlap by default - each occupies
its own quarter/half/three-quarter/full-width slot and wraps to new rows as
needed. `.pin-lines` keeps `overflow: hidden`, so very dense topics (many
ranges in one book) clip extra rows rather than overflowing the card; the
`expand-verses-btn` remains the full-detail entry point. `isolation: isolate`
and `.pin-line`'s `mix-blend-mode: screen` are kept for the remaining
hover-overlap edge cases.

## The four datasets (`DATASET_CONFIG`, `js/app.js` ~line 34)

All four share one schema and are loaded generically by `loadTopics()`:

```json
{
  "TOPIC OR WORD NAME": {
    "name": "TOPIC OR WORD NAME",
    "references": {
      "BOOKID": [ { "verse": <absolute verse index>, "subtopics": [...], "refs": ["Gen 1:1"] } ]
    },
    "books": ["BOOKID", ...]
  }
}
```

| Dropdown label | `DATASET_CONFIG` key | File | Source |
|---|---|---|---|
| Nave's Topics | `topics` | `data/topics-with-references.json` (~19MB) | Nave's Topical Bible (`scripts/parse-topics.js`) |
| BSB Topics | `bsb-topics` | `data/bsb-topics-with-references.json` | `C:\Unity Projects\_BibleDatasets\Berean\bsb_topical_index.xlsx` via `scripts/parse-bsb-topics.js` |
| Prophecy | `prophecy` | `data/prophecy-topics-with-references.json` | Prophecy docx parse (separate aggregate-topic logic, `PROPHECY_AGGREGATE_TOPICS`) |
| BSB Concordance | `concordance` | `data/bsb-concordance-with-references.json` (14.77MB, 14,526 words, 276,602 refs) | `C:\Unity Projects\_BibleDatasets\Berean\bsb_concordance.xlsx` via `scripts/parse-bsb-concordance.js` |

### Shared helpers: `scripts/lib/bsb-shared.js`
Used by both `parse-bsb-topics.js` and `parse-bsb-concordance.js`:
- `BOOK_IDS` — book name/abbreviation → 3-letter ID map. Extends the Nave's
  Topics map with full Berean book names/abbreviations (incl. 30 aliases added
  for the Concordance's `Verse`-column abbreviations like `Exo`, `1Ki`, `1 Joh`,
  `Sos`, `Tts`, `Jam`, `Jde`, etc.).
- `loadBibleData()` / `getAbsoluteVerseIndex(bibleData, bookId, chapter, verse)` —
  exact absolute-verse-index lookup against `data/bible.json`, mirroring the
  runtime `getAbsoluteVerseIndex` in `js/app.js`.

### BSB Concordance stopword strategy (`scripts/parse-bsb-concordance.js`)
The raw concordance has 14,782 distinct words / 726,744 occurrences — too
large to eager-load alongside the other datasets. Words are filtered via:
- `KEEP_WORDS` (26 words) — high-frequency but meaningful proper
  nouns/theological terms kept regardless of frequency: Lord, God, Jesus, Son,
  King, Man, People, Israel, Land, Day, Men, House, Father, David, Sons, Hand,
  Moses, Judah, Jerusalem, City, Earth, Name, Offering, Word, Heart, Egypt.
- `DISCARD_WORDS` (117 words) — the >=600-occurrence function words (the, and,
  of, to, etc.), minus `KEEP_WORDS`.
- `EXTENSION_WORDS` (~117 words) — lower-frequency function words in the same
  categories (pronouns, conjunctions, prepositions, archaic KJV/BSB forms like
  thee/thou/hath/unto, quantifiers), excluded at any frequency. Spelled-out
  numbers (Three..Twelve, Twenty..Thousand, First..Tenth, Once/Twice/Thrice)
  were removed from this list — numbers like 7, 12, 40, 70 carry real
  theological significance (e.g. "Seven" → 375 refs), so they're now kept.
- `STOPWORDS = DISCARD_WORDS ∪ EXTENSION_WORDS` (lowercased). A word header
  (`Entry` matching `/^(.+?)\s*\((\d+)\s*Occurrence/` on `Occ === 0` rows) is
  skipped if it's a stopword and not in `KEEP_WORDS`.
- Result: 14,559 words, 280,601 references, 14.97MB minified — same order of
  magnitude as `data/bible.json` (~6MB), so eager-loading is feasible.
- `parseVerseRef()` handles both `"Gen 32:15"` and the ~10 malformed
  underscore-separated rows (`"Lev_26:5"`).

### Phrase entries (`PHRASE_ENTRIES`)
The source xlsx is single-word only, so multi-word phrases that carry their
own theological weight (e.g. "Son of Man") don't exist as concordance entries
even though the underlying words do. `PHRASE_ENTRIES` (currently just
`['Son of Man']`) is scanned separately: after the main word-entry loop,
`parseConcordance` iterates every book/chapter/verse in `bibleData` (from
`loadBibleData()`) and tests `\b<phrase>\b` (case-sensitive) against
`verse.text`. Matches are converted to `{ verse: <absoluteVerse>, subtopics: [],
refs: ["<Abbrev> <chapter>:<verse>"] }` entries via `getAbsoluteVerseIndex` and
a new `BOOK_ABBREVIATIONS` map (bookId → xlsx-style abbreviation, e.g.
`EZK → "Eze"`, `1JN → "1 Joh"`), then merged into `result` before the existing
per-book sort/`books`-array pass so they're indistinguishable from word
entries downstream. "Son of Man" → 82 references across Matthew, Mark, Luke,
John, Acts, Daniel, and Revelation (the capitalized Messianic title — the
lowercase "son of man" address to Ezekiel doesn't match).

## Known pre-existing quirk: dataset-switch fallback topic
Switching the Dataset dropdown to one where the current topic name doesn't
exist (e.g. Nave's `"JESUS, THE CHRIST"` isn't a key in BSB Topics or the
Concordance) falls back to `getPreferredTopicFallback()` →
`allTopicNames[0]` (alphabetically first topic/word, e.g. "AARON"). This is
pre-existing behavior (also happens switching Prophecy → Nave's Topics), not a
regression from adding BSB Topics/Concordance, and no fix is currently
planned.

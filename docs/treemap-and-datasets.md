# Overview treemap sizing & topic/concordance datasets

Reference notes for the Overview ("Bible View") treemap layout and the four
topic/reference datasets behind the Dataset dropdown. Written so future work
on book sizing, pin-line rendering, or new datasets doesn't have to
rediscover this from scratch.

## Overview treemap sizing (`js/app.js`)

### Data source: character counts
- `data/book-character-counts.json` — `{ metadata: {...}, books: { GEN: 182159, ..., REV: ... } }`,
  one entry per book, summed from `verse.text.length` across every chapter/verse
  in `data/bible.json`.
- Generated by `scripts/compute-character-counts.js` (run once, output committed).
- `buildItems()` (~line 1109) sets each item's `value` to
  `characterCounts[book.id]` (falling back to `verseCount`, then `1`). The
  synthetic `SEPARATOR` item ("0 AD", inserted after MAL) has a fixed
  `value: 100`.

### Layout: `enforceAspectRatios(items, width, height)` (~line 1209)
14 fixed-width columns; each item's height is derived from its `value`. Two
problems showed up once real character counts were used directly:

- Character counts span **~138x** (Jeremiah 207,838 vs. 2 John 1,502), so a
  linear value→height mapping plus the `minHeight = 110` floor (needed to fit
  3 pin lines) caused ~73% of cards to clamp to the same 110px floor.
- The old fixed `booksPerCol = ceil(items.length / 14)` slice assigned books
  to columns in groups of 5 regardless of actual content height, so a column
  could have a couple hundred px of empty space below its last book while the
  next book was forced into a new column (e.g. 1 Kings vs. 2 Samuel).

Current approach:
1. **Sub-linear weight** — `item.sizeWeight = Math.pow(item.value, 0.3)`.
   Compresses the 138x range to ~4.4x so short books differentiate from each
   other above the floor instead of all clamping identically. (0.3 was chosen
   empirically via `scripts/verify-treemap-packing.js` - sqrt (0.5) only got
   the floor count down to ~54% at HD; 0.3 gets it to ~45% at HD and ~6% at
   4K while still giving the largest books a clearly taller ~2x silhouette.)
2. **Greedy shelf packing** (`packColumns(unitHeight)`) — walk items in
   canonical order (Genesis → Revelation, with the "0 AD" separator after
   Malachi), accumulating into the current column until the next item would
   overflow `height`, then start a new column (capped at 14). Preserves
   reading order while letting columns absorb however many books fit.
3. **Binary search for `unitHeight`** — 25 iterations searching for the
   smallest `unitHeight` where `packColumns` uses all 14 columns (too small
   leaves trailing columns empty, too large overflows the last column).
4. **`scaleFactor` squeeze** — if the densest resulting column still slightly
   overflows `height` after the binary search, scale all heights down
   uniformly to fit.
5. **Per-column `fillFactor` stretch** — after `scaleFactor`, any column whose
   total height is *less* than `height` (commonly the last column or other
   columns near the start of the search range that ended up sparser) is
   stretched uniformly so it sums to exactly `height`, capped at
   `MAX_COLUMN_FILL_FACTOR = 1.3`. This eliminates empty space below the last
   card in most columns and gives every card a bit more room for pin lines.
   The cap exists because the final column (2/3 John, Jude, Revelation at HD)
   is mostly 110px-floor items, so its uncapped `fillFactor` (~1.7) stretched
   Revelation to ~268px — taller than Matthew (~217px) despite having half its
   character count, visually implying Revelation is the longest book. At 1.3,
   Revelation lands at ~204px (HD) / ~354px (4K), smaller than Matthew/John as
   expected, leaving a modest gap at the bottom of that one column.

`item.value` (raw character count) is left untouched; `item.sizeWeight` is a
layout-only derived field. This is resolution-independent (works for both HD
and 4K, since `height` is the actual rendered viewport height passed in by the
caller).

Dead code, not used by the final layout: `normalizeAreas`, `worst`,
`layoutRow`, `squarify` (~lines 1136-1207, a squarified-treemap algorithm from
an earlier approach). The Book View chapter treemap is a separate code path
(verse-count based) and is out of scope for all of the above.

`scripts/verify-treemap-packing.js` is a standalone (not runtime) Node script
that re-implements this algorithm against the real
`data/book-character-counts.json` and prints the resulting column packing,
floor-clamped item count, and 1 Kings/2 Samuel placement for representative
HD/4K dimensions - useful for re-tuning the exponent or `minHeight` without a
browser.

## Pin-line rendering

Topic/word references render as small horizontal "pin lines" inside each
book card, positioned by vertical percentage within the book.

**Recipe note**: this was built for the Bible state (Overview/`renderTreemap`,
book cards) and the same pattern was mirrored into the Book state
(`renderBookView`, chapter cards) - both are done and described below. Neither
the Chapter state (`renderReadView`, a single-chapter text reading view) nor
the Verses state (`renderVersesView`, a flat cross-book list of every verse
for the topic) uses pin-lines, so this recipe doesn't apply to either.

- **Overview**: `renderTreemap` (~line 1330-1460+).
- **Book View**: `renderBookView` has an equivalent block (~line 1798-1845)
  for chapter cards — same logic, mirrored.

Mechanics:
- For each reference, `getAbsoluteVerseIndex(bookId, chapter, verse)` gives an
  absolute verse index within the book; consecutive absolute-verse indices are
  merged into ranges (no spatial/positional deduplication beyond this), then
  each range's first verse gets a `percentage` (`absoluteVerse / totalVerses`
  for Overview, `entry.verse / chapterVerseTotal` for Book View).
- **Vertical bands** — `.pin-lines` is a `flex-direction: column` container of
  `PIN_LINE_BANDS = 8` (~line 285, near `getPinLineWidthPercent`) stacked
  `.pin-line-band` divs, each `flex: 1` (so they evenly split the card's pin
  area regardless of how many bands have content). Each range is assigned to
  `bands[getPinLineBandIndex(range.verses[0].percentage)]` —
  `getPinLineBandIndex` maps the 0-100 percentage to a 0..7 band index. Empty
  bands render as blank space, which is the visual cue for "no references in
  this part of the book/chapter". This makes a topic whose only reference is
  near the end of a book (e.g. BSB Concordance "Word" in 1 Corinthians 14:36,
  ~80% through the book → band 6) render near the bottom of the card instead
  of the top, while a dense topic (e.g. "Lord" in 1 Corinthians, 61 refs)
  naturally spreads across most/all bands and fills the card as before.
- Within a band, `.pin-line-band` is a `flex-wrap` flow container (same as the
  old whole-`.pin-lines` behavior). Each range's `.pin-line` gets an inline
  `flexBasis` from `getPinLineWidthPercent(verseCount)` (~line 283): 1 verse →
  25%, 2-3 → 50%, 4-6 → 75%, 7+ → 100%. Ranges within a band render in
  book/chapter reading order (already sorted by absolute verse position), so
  pins flow left-to-right, top-to-bottom like text within their band.
- Ranges >10 verses additionally get `.pin-line-wrapped` (thinner, brighter;
  combined with the 100% flexBasis from the tier above).
- `.pin-line--ot` / `--nt` / `--mixed` color the line by whether its
  reference(s) fall in the OT, NT, or both.

This replaced an earlier absolute-positioned layout (`top: <percentage>%`,
continuous width formula `Math.min(20 + (verseCount-1)*8, 100)`) that
left-pinned every range to its own full-width vertical slot regardless of
verse count - wasting most of the row for the common single-verse case and
giving high-frequency words no way to show more than one pin per row. It also
replaced an intermediate flex-wrap-everything layout that, while solving the
overlap/width problem, lost positional information entirely - every topic's
pins started in the top-left of the card regardless of where in the book they
actually occurred.

### Overlap handling
Within a band, pins no longer overlap by default - each occupies its own
quarter/half/three-quarter/full-width slot and wraps to new rows as needed.
`.pin-line-band` keeps `overflow: hidden`, so a band with many ranges clips
extra rows rather than overflowing into adjacent bands; the
`expand-verses-btn` remains the full-detail entry point. `isolation: isolate`
and `.pin-line`'s `mix-blend-mode: screen` are kept for the remaining
hover-overlap edge cases.

### 4K header clearance
`.pin-lines` defaults to `top: 32px`, sized for the base `.card-title-bar`
(~25-28px tall). The `@media (min-width: 2560px)` block enlarges
`.card-title-bar` (`font-size: 1rem; padding: 10px 12px`, ~40-44px tall), so
it adds a matching `.pin-lines { top: 44px; }` override in the same media
query. This is a low-specificity rule and doesn't affect the more specific
`#book-grid[data-density="high"/"ultra"] .pin-lines` overrides used by
high-chapter-count books in Book View.

## The seven datasets (`DATASET_CONFIG`, `js/app.js` ~line 34)

All seven share one schema and are loaded generically by `loadTopics()`:

```json
{
  "TOPIC OR WORD NAME": {
    "name": "TOPIC OR WORD NAME",
    "references": {
      "BOOKID": [ { "verse": <absolute verse index>, "subtopics": [...], "refs": ["Gen 1:1"] } ]
    },
    "books": ["BOOKID", ...],
    "bio": { "subtitle": "...", "text": "...", "family": "...", "alsoCalled": "...", "mapUrl": "..." }
  }
}
```

`bio` is optional and currently only present in People/Places (see below) - every piece inside
it is independently optional too, omitted when there's nothing to say. `topicsData[name].bio`
is read directly at render time (`applyTopicBioAffordance`, `js/app.js` ~line 3993) to decide
whether the `.state-current-topic` label (all four states) gets a click affordance; clicking
opens `showTopicBioModal`, reusing the same `.verse-modal-*` CSS as `showBookSummaryModal`
(with a `.verse-modal-content--bio` modifier forcing `flex-direction: column`, since the split
layout those classes were built for doesn't suit a single scrolling column of text).

### Custom Dataset pipeline (`source/custom-topics.json` → `scripts/build-custom-dataset.js`)
The only dataset the developer hand-authors rather than parses from a third-party
source — for personal study (e.g. "Jesus is God" with supporting verses), added to
over time. `source/custom-topics.json` is a flat `{ "Topic Name": ["Book Ch:V", ...] }`
map kept deliberately simple to hand-edit; each ref string may be a single verse
("John 1:1"), a verse range ("John 1:1-3"), a comma list ("John 1:1,3"), and/or end
with `| a note` (becomes that verse's `subtopics` entry) or `| a theme | a note` (emits
`[theme, note]` - the theme is a short label shared verbatim by every verse making the
same point, so the app's subtopic-filter dropdown can group them; the note stays
per-verse commentary). The app hides one-verse groups for this dataset
(`SUBTOPIC_FILTER_MIN_PASSAGES` in `js/app.js`), so the dropdown lists only recurring
themes - "Jesus is God" is the worked example. Workflow: edit
`source/custom-topics.json`, run `node scripts/build-custom-dataset.js` to regenerate
`data/custom-topics-with-references.json` (computing each absolute verse index against
`data/bible.json`, same approach as `scripts/parse-prophecy-docx.js`), then commit both
files. `DATASET_CONFIG.custom` also carries a `note` string, surfaced next to the
dataset label in the UI (`updateDatasetUI()`, `js/app.js` ~line 856) so it's clear this
dataset isn't a sourced text like the other four.

### Nave's Topics pipeline (`source/Naves.txt` → `scripts/parse-naves-text.js` → `scripts/parse-topics.js`)
Two-stage pipeline, same as the other three datasets' "raw source → intermediate
JSON → final JSON" shape: `parse-naves-text.js` reads the source and writes
`data/topics-input.json` (`{ topics: [{ name, verses }] }`, `name` like
`"TERM - subtopic"`); `parse-topics.js` resolves book IDs, expands verse
ranges/positions, and writes the final `data/topics-with-references.json`.
Both stages share `scripts/lib/naves-book-ids.js`'s `BOOK_IDS` map.

**Why a plain-text source instead of the original THML/XML.** The original
source (`C:\Unity Projects\_BibleDatasets\Naves\Naves.xml`, a CCEL THML
export, parsed by a now-deleted `scripts/parse-naves-thml.js`) had three
data-loss bugs discovered while investigating a user report that topic
"JOSIAH" was missing `2 Kings 21:24-26`:
1. The old `parseVerseReference` regex excluded leading digits from the book
   group, so **every** reference to a `1`/`2`/`3`-prefixed book abbreviation
   (`1Sa`, `2Ki`, `1Ch`, `2Co`, `1Th`, `1Ti`, `1Pe`, `1Jo`/`2Jo`/`3Jo`) was
   silently dropped, across every topic in the dataset.
2. `BOOK_IDS` mapped `'Jud'` (the actual abbreviation for **Judges**) to
   Jude's book code, so ~2,400 Judges verse-refs were filed under the
   25-verse epistle of Jude instead.
3. The THML edition itself had lost per-verse granularity for the five
   one-chapter books (Obadiah, Philemon, 2 John, 3 John, Jude) - every single
   citation to them, across the whole file, collapsed to chapter 1 verse 1
   (`parsed="|Jude|1|1|0|0"` for all 115 Jude citations, etc.) - a
   limitation of that specific digitization, unrecoverable from that source.

Switching to the CCEL plain-text edition (`source/Naves.txt`, fetched
separately, **not** derived from the XML) fixed all three: bugs 1-2 were
parser bugs (now fixed in `BOOK_IDS`/the regex regardless of source), and the
plain text turned out to retain real verse numbers for the one-chapter books
(e.g. distinct `Jude 1:7`, `1:9`, `1:14`, `1:24`, ... - all 25 verses
eventually cited) that the XML had lost. `parseVerseReference` in
`parse-topics.js` still has a `SINGLE_CHAPTER_BOOK_IDS` allowance for a bare
`Book N` (no colon) on those five books specifically, treating `N` as the
verse in chapter 1 - now mostly unused since the text source has real
verses, but kept as a safety net.

**Text format parsing (`parse-naves-text.js`).** The CCEL plain-text export
has three indentation levels: term headings (3-space indent, e.g. `   AARON`),
`-`/`.` bullets (10-space indent, `-` = top-level, `.` = nested), and
wrapped continuation lines (also 10-space indent, no `-`/`.` prefix - appended
to the previous bullet with a single space). A handful of entries add a
fourth, unmarked level: a `-`/`.` header with no refs of its own, followed by
several blank-line-separated paragraphs with no `-`/`.` prefix at all, one
per sub-item (e.g. ARMIES' ".Methods employed in effecting" → "Sounding a
trumpet ..." / "Cutting oxen in pieces ..."). A blank line immediately before
such a line means "new sub-item," not "continuation of the previous
line" - that distinction is what `precededByBlank` tracks.

Within each bullet, `splitLabelAndRefs()` finds where the descriptive label
ends and the first scripture reference begins via `FIRST_REF_BOUNDARY`, a
regex built from `BOOK_IDS` keys - but restricted to short/digit-prefixed/
abbreviation-shaped keys only (`Ex`, `2Ki`, `1Co`, ...), excluding full
spelled-out names (`Jonah`, `Micah`, `Amos`, `Mark`, `Luke`, `John`, `James`,
`Titus`, ...) because those double as ordinary person/place names within
label text (e.g. "Father of **Jonah**" was mis-split before this exclusion,
since the regex matched "Jonah" as if it were the book). `Jude` is kept as a
special case since it has no shorter alias. Two genuinely irreducible
collisions remain and are accepted as a known limit: `So` (Song of Songs
abbreviation *and* the Egyptian king's name in 2 Ki 17:4) and `Dan`
(Daniel abbreviation *and* the tribe of Dan) - both are too short to safely
exclude without breaking far more legitimate citations than the 1-2 false
positives each causes.

`normalizeReferenceSequence()` also handles: `with X` as a "same book,
compare also" connector rather than label text (e.g. `1Sa 22:20-23; with
22:6-19`); line-wrap artifacts where a long comma list got rejoined with a
stray space (`84, 107` → `84,107`); and `.`-as-row-separator in two large
OT/NT cross-reference tables (`QUOTATIONS AND ALLUSIONS...`, `PROPHECY -
OLD TESTAMENT MESSIANIC PASSAGES...`) that use periods instead of semicolons
between rows. Pure `-See [N]TARGET` cross-reference redirects are parsed but
discarded (no scripture refs to show) - not wired up as search aliases.

**Numbered-sense disambiguation.** Some terms have multiple numbered
top-level senses, each a distinct person/place, e.g.:
```
   JOHN
          -1. The Baptist          <- header, no refs of its own
          .Prophecies concerning Isa 40:3; ...   <- belongs to sense 1
          -2. The Apostle          <- header, no refs of its own
          .Intimately associated with Jesus Joh 13:23-26; 21:20   <- belongs to sense 2
```
Found via `grep` to affect 125+ terms (ISRAEL has 21 senses, EPHRAIM 3, plus
DANIEL, ELIJAH, AZARIAH, BABYLON, ...). Two strategies, both tracked via
`activeSense` (the active `-N. Label` header) in the per-term bullet loop:
- **General case**: the active sense is folded into the **subtopic** label
  (e.g. JOSIAH's `.Ancestor of Jesus` → `1. King of Judah - .Ancestor of
  Jesus`), so tooltips disambiguate. No `js/app.js` changes needed -
  tooltips just render whatever string is in a verse's `subtopics` array.
- **`SPLIT_NUMBERED_SENSE_TERMS`** (`JOHN`, `JAMES`, `MARY`, `SIMON`,
  `PHILIP` - cherry-picked, not auto-detected): the active sense is folded
  into the **term** instead, using `": "` rather than `" - "` so
  `parse-topics.js`'s `splitTopicName` (which splits on the first `" - "`)
  doesn't re-merge it back into the base term. Each sense becomes its own
  top-level dropdown entry (`"JOHN: 1. The Baptist"`, `"JOHN: 2. The
  Apostle"`, and a `"JOHN: 3. A relative of Annas the high priest"` nobody
  had noticed) - there is intentionally **no bare `"JOHN"` entry** anymore.
  Extending this list is a one-line change to the `SPLIT_NUMBERED_SENSE_TERMS`
  `Set` near the top of `parse-naves-text.js`.

### BSB Topics section-boundary handling (`scripts/parse-bsb-topics.js`)
The source xlsx is one continuous alphabetical index, not a clean tree: between
one `[Top]`-marked topic and the next, `[Nav]`/`[TTT]` rows are sometimes
genuine subtopics of the current topic (e.g. "Entertainments: ..." under
"Entertainment") but sometimes unrelated alphabetical entries that never got
their own `[Top]` row (e.g. "Song of Moses..."/"Envy: ..."/"Ephraim: ..."
appearing between "Son of God" and "Songs"). A `[Nav]`/`[TTT]` label is
treated as a genuine subtopic only if its text before the first `:` (lowercased)
`startsWith()` the current topic's name (covers plurals like "Entertainment" →
"Entertainments"); otherwise `suppressVerses = true` until the next genuine
subtopic or `[Top]` row, and its verse rows are dropped. Fixed several
misattributed-verse bugs: "Son of God" (was 60 refs incl. unrelated "Song of..."
entries, now 10), "Blood of Jesus" (no longer includes a Habakkuk verse from
"Blood of Judgments"), "Entertainment" (was 680 refs incl. "Envy"/"Ephraim"/
"Epicurean" subtopics, now 143).

### Shared helpers: `scripts/lib/bsb-shared.js`
Used by both `parse-bsb-topics.js` and `parse-bsb-concordance.js`:
- `BOOK_IDS` — book name/abbreviation → 3-letter ID map. Extends the Nave's
  Topics map with full Berean book names/abbreviations (incl. 30 aliases added
  for the Concordance's `Verse`-column abbreviations like `Exo`, `1Ki`, `1 Joh`,
  `Sos`, `Tts`, `Jam`, `Jde`, etc.).
- `loadBibleData()` / `getAbsoluteVerseIndex(bibleData, bookId, chapter, verse)` —
  exact absolute-verse-index lookup against `data/bible.json`, mirroring the
  runtime `getAbsoluteVerseIndex` in `js/app.js`.

### BSB Concordance stopword strategy (`scripts/parse-bsb-concordance.js`)
The raw concordance has 14,782 distinct words / 726,744 occurrences — too
large to eager-load alongside the other datasets. Words are filtered via:
- `KEEP_WORDS` (26 words) — high-frequency but meaningful proper
  nouns/theological terms kept regardless of frequency: Lord, God, Jesus, Son,
  King, Man, People, Israel, Land, Day, Men, House, Father, David, Sons, Hand,
  Moses, Judah, Jerusalem, City, Earth, Name, Offering, Word, Heart, Egypt.
- `DISCARD_WORDS` (117 words) — the >=600-occurrence function words (the, and,
  of, to, etc.), minus `KEEP_WORDS`.
- `EXTENSION_WORDS` (~117 words) — lower-frequency function words in the same
  categories (pronouns, conjunctions, prepositions, archaic KJV/BSB forms like
  thee/thou/hath/unto, quantifiers), excluded at any frequency. Spelled-out
  numbers (Three..Twelve, Twenty..Thousand, First..Tenth, Once/Twice/Thrice)
  were removed from this list — numbers like 7, 12, 40, 70 carry real
  theological significance (e.g. "Seven" → 375 refs), so they're now kept.
- `STOPWORDS = DISCARD_WORDS ∪ EXTENSION_WORDS` (lowercased). A word header
  (`Entry` matching `/^(.+?)\s*\((\d+)\s*Occurrence/` on `Occ === 0` rows) is
  skipped if it's a stopword and not in `KEEP_WORDS`.
- Result: 14,559 words, 280,601 references, 14.97MB minified — same order of
  magnitude as `data/bible.json` (~6MB), so eager-loading is feasible.
- `parseVerseRef()` handles both `"Gen 32:15"` and the ~10 malformed
  underscore-separated rows (`"Lev_26:5"`).

### Phrase entries (`PHRASE_ENTRIES`)
The source xlsx is single-word only, so multi-word phrases that carry their
own theological weight (e.g. "Son of Man") don't exist as concordance entries
even though the underlying words do. `PHRASE_ENTRIES` (currently just
`['Son of Man']`) is scanned separately: after the main word-entry loop,
`parseConcordance` iterates every book/chapter/verse in `bibleData` (from
`loadBibleData()`) and tests `\b<phrase>\b` (case-sensitive) against
`verse.text`. Matches are converted to `{ verse: <absoluteVerse>, subtopics: [],
refs: ["<Abbrev> <chapter>:<verse>"] }` entries via `getAbsoluteVerseIndex` and
a new `BOOK_ABBREVIATIONS` map (bookId → xlsx-style abbreviation, e.g.
`EZK → "Eze"`, `1JN → "1 Joh"`), then merged into `result` before the existing
per-book sort/`books`-array pass so they're indistinguishable from word
entries downstream. "Son of Man" → 82 references across Matthew, Mark, Luke,
John, Acts, Daniel, and Revelation (the capitalized Messianic title — the
lowercase "son of man" address to Ezekiel doesn't match).

### People / Places (`scripts/parse-theographic-people.js` / `-places.js`, `scripts/lib/theographic-shared.js`)
Source: [Theographic Bible Metadata](https://github.com/robertrouse/theographic-bible-metadata)'s
`json/people.json` / `places.json` / `verses.json` / `peopleGroups.json`, read from
`C:\Unity Projects\_BibleDatasets\GospelGo_GoMap_Datasets\RawDataInclude\theographic-bible-metadata-master\theographic-bible-metadata-master\json`
(`THEOGRAPHIC_JSON_DIR` in the shared lib). Added as a non-scholarly counterpart to BSB
Concordance: Concordance already gives an exhaustive literal-text match for any name (its
"Moses" has more refs than Theographic's own curated list), so People/Places isn't trying to
out-exhaustive it — the value is *identity* (disambiguating distinct same-named people/places)
and friendly metadata (birth/death years, family, a plain-language Easton's blurb) via the `bio`
field, surfaced through a click-to-open modal rather than cluttering the search/treemap UI.

- Each verse ID (from a person/place's `verses` array) resolves to an OSIS ref
  (`Gen.1.1`) via a book/chapter/verse map built from `verses.json`, then to this
  app's 3-letter book ID (`OSIS_TO_BOOK_ID` in `theographic-shared.js` = the shared
  `BOOK_IDS` from `bsb-shared.js`, plus `OSIS_BOOK_ALIASES` for exact OSIS spellings
  it doesn't already cover — `1Sam`/`2Sam`/`1John`/`2John`/`3John`/`Obad`/`Phlm`/`Esth`/`Prov`),
  then to an absolute verse index the same way every other parser does
  (`getAbsoluteVerseIndex` against `data/bible.json`). Verified empirically: 0 unknown
  book prefixes across all 66 books once those aliases were added.
- `BOOK_ABBREVIATIONS` (bookId → "Exo"/"1 Joh"/etc. citation style) was promoted from
  `parse-bsb-concordance.js` into `scripts/lib/bsb-shared.js` so all three parsers
  generate `refs` strings in the same format, rather than keeping three copies of the
  same object in sync by hand.
- **Undisambiguated-homonym merging.** Theographic's `displayTitle` is meant to be a
  unique, disambiguated name ("Jacob (Israel)", "Abiel (Arbathite)"), but a large share
  of minor/genealogical records are never actually disambiguated in the source itself
  (flagged `ambiguous: true` — e.g. three unrelated "Abiah" records: Samuel's son, Hezron's
  wife, and a son of Becher, with no distinguishing info beyond the bare name). Discovered
  by the parser's own duplicate-key warnings on the first run: **427 of 1,870** distinct
  person names (1,599 of 3,042 eligible records) collide this way; 84 of 1,158 place names
  (190 records) do too. Records sharing a `displayTitle` are grouped and merged into one
  *topic* (verse references are unioned, deduping a verse ID that mentions more than one
  merged person so it doesn't appear twice) — but **not** into one merged *bio*. An earlier
  version intersected every record's fields (`commonValue()`, now removed) so a field only
  survived if every record in the group agreed on it; in practice this was actively
  misleading rather than merely conservative — e.g. "Abiah"'s intersected bio showed
  `Spouse: Hezron · Children: Ashur` with nothing to indicate that's only true of *one* of
  the three Abiahs (the other two simply had no spouse/children field to conflict with it),
  and it discarded all three individuals' own Easton write-ups outright, since those almost
  never match verbatim across unrelated people. `buildPersonBio()`/`buildPlaceBio()` now
  build each record's bio independently, with nothing compared or merged; a group of more
  than one becomes `{ subtitle: "N biblical people/places share this name", people: [...] }`,
  one self-contained bio per record, and `showTopicBioModal` (`js/app.js`) renders each as
  its own numbered, divider-separated block (`.topic-bio-person`) instead of trying to
  present one unified answer for what's really several different people/places.
- `alsoCalled` (people) / `aliases` (places) are raw comma-separated strings with no
  guaranteed spacing (e.g. Jesus Christ's is `"Lord,Son,Lamb,Saviour,..."`) —
  `formatCommaList()` splits/trims/rejoins with `", "` before it reaches the bio.
- `bio.text` is an array of paragraphs, not one string. Easton's `dictionaryText` has no
  real line breaks - `splitDictionaryParagraphs()` (`theographic-shared.js`) splits on runs
  of 4+ spaces, which the source markup leaves exactly where a paragraph break belongs
  (verified empirically: always follows a sentence-ending period). Shorter 2-3 space runs
  are unrelated padding around inline scripture citations (`"(  Genesis 45:17-25  )"`) and
  are collapsed to a single space per-paragraph instead of being treated as breaks. Also
  decodes the handful of entries with a stray literal `&nbsp;`/`&amp;` left over from the
  source. `showTopicBioModal` (`js/app.js`) renders each array element as its own `<p>`.
- **`dictionaryText` vs `dictText` fallback.** Theographic exports two forms of the same
  Easton's entry: `dictionaryText` (plain text, 2-3 space padding around citations) and
  `dictText` (a 1-element markdown array, real `\n` line breaks, citations as markdown
  links like `[1 Chr. 7:8](/1chr#1Chr.7.8)`). `dictionaryText` is only populated for a
  small, better-documented subset — verified empirically: of people/places with *some*
  Easton entry, **1,693 of ~1,934 people** and **862 of ~1,059 places** have `dictText` but
  no `dictionaryText` at all. The first version of these parsers only read `dictionaryText`,
  so the large majority of entries silently showed no bio text whatsoever (this is exactly
  why none of "Abiah"'s three merged people originally had any). `getEastonParagraphs()`
  now prefers `dictionaryText` when present and falls back to `dictText[0]` otherwise,
  via a parallel `splitDictTextParagraphs()` that strips markdown links down to their
  citation text (`stripMarkdownLinks()`) and splits on `\n+` instead of 4+ spaces.
- Places additionally get a `mapUrl` in their bio, linking to GospelGo's own map app
  (`C:\Unity Projects\Builds\BiblePlaces`, deployed at `https://bibleplaces.gospelgo.org`)
  rather than a generic Google Maps pin - its deep-link contract (`src/deepLink.ts`)
  takes the Theographic `slug` directly (`?place=<slug>`, or `?places=<slug1>,<slug2>`
  for several), which a merged group of undisambiguated same-named places maps onto
  exactly: every merged place's slug goes into one `?places=` link rather than picking
  just one and losing the others. Rendered as "Open in Bible Places" in the bio modal.
- `defaultTopic`: People → `"Jesus Christ"`, Places → `"Jerusalem"` (both exist as exact
  keys in the generated files — verified directly rather than assumed, since Theographic
  has separate `"Jesus"` and `"Jesus Christ"` records).

## Per-dataset default topics
Each `DATASET_CONFIG` entry has a `defaultTopic` (resolved via
`getDatasetDefaultTopic(mode)`, near `getPreferredTopicFallback()`):
Nave's Topics → `"JESUS, THE CHRIST"`, BSB Topics → `"Light"`,
Concordance → `"Eternal"`, Prophecy → `""` (blank - `getDatasetDefaultTopic`
returns `null` for an empty `defaultTopic` rather than falling back, so
Prophecy starts with no topic selected and an empty search field).
`getDatasetDefaultTopic` is used for: initial boot (no stored topic), the
search field's clear/reset button when on Overview, and the dataset-switch
handler when the previously-selected topic doesn't exist in the new dataset
(e.g. Nave's `"JESUS, THE CHRIST"` isn't a key in BSB Topics or the
Concordance - falls back to that dataset's own default instead of the
alphabetically-first topic). `loadTopics()` always calls
`updateTopicOptions("")` after loading, so the `<datalist>` is populated with
all topic names even when the input is blank (Prophecy) - clicking the field
shows the full dropdown.

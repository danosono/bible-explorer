# Bible Explorer

Static site (vanilla HTML/CSS/JS, no build step) — interactive treemap-style explorer of the Bible by topic/prophecy. Live at https://bible-explorer.gospelgo.org.

## Stack & entry points
- `index.html` — single page, all views (Bible/Book/Chapter/Verses "states") live in here.
- `js/app.js` — all application logic (~3000 lines). `js/book-metadata.js` is static per-book metadata (genre, author, etc.).
- `css/style.css` — the **only** active stylesheet (loaded with `css/normalize.css`). It's plain CSS with custom properties (`--text-1`, `--accent-1`, etc. in `:root`).
- `data/` — large JSON datasets: `bible.json`, `data/books/`, `data/chapters/` (full text), `topics-with-references.json` (~19MB, Nave's Topics), `prophecy-topics-with-references.json`.
- `scripts/` — one-off Node scripts used to generate/parse the data files (USFM, Nave's topics, prophecy docx, etc.). Not part of the runtime app.
- `source/Naves.txt` — the plain-text CCEL edition of Nave's Topical Bible; the only checked-in raw source doc (others live outside the repo). Build-time only — never fetched by the app. See "Nave's Topics pipeline" in `docs/treemap-and-datasets.md` for why it replaced an XML source and what bugs that fixed.

## Stale files — ignore
`css/base.css`, `components.css`, `layout.css`, `responsive.css`, `states.css`, and `_refactor_matches.txt` are all **empty (0 bytes)** — leftovers from an abandoned modular CSS refactor (Mar 2026). `_style_pre_modular.css` and `style.css.bak` are old backups. ## Local dev server gotcha
`server.js` (`node server.js`, port 8000) is a tiny static file server that does **not** strip query strings — `index.html` references `js/app.js?v=NN` (cache-busting), which 404s under `server.js`. For testing/screenshots, use something that handles query strings, e.g. `npx http-server -p 8001 -s`.

## Topic system (js/app.js)
- `DEFAULT_TOPIC` (~line 25) — Nave's Topics' default, `"JESUS, THE CHRIST"`. Each `DATASET_CONFIG` entry also has its own `defaultTopic` (BSB Topics: `"Light"`, Concordance: `"Eternal"`, Prophecy: `"[All] OT + NT Combined"` — one of the synthetic aggregate topics, see below, Custom Dataset: `"Jesus is God"`). `getDatasetDefaultTopic(mode)` resolves the right one; an empty-string `defaultTopic` (none currently) would return `null` and leave the search field blank, with the custom `#topic-suggestions` listbox (see below) still populated.
- `FALLBACK_NAV_TOPIC` — used if `DEFAULT_TOPIC` can't be resolved.
- Topic keys are UPPERCASE strings in `data/topics-with-references.json` (e.g. `"JESUS, THE CHRIST"`, `"LOVE"`, `"FAITH"`); other datasets use natural-case keys.
- `normalizeTopicKey()` (trim + lowercase) and `resolveTopicKey()` (looks up `topicsIndex` map) handle case-insensitive matching — you can set `DEFAULT_TOPIC` in any case.
- `DATASET_CONFIG` (~line 62) switches between its datasets (the five described here plus People, Places and the generated **Types of Christ**, `types-of-christ` - built by `scripts/build-types-of-christ.js` from the sibling game repo `GospelGoWebApp`'s `motifs.json` + quests, never hand-edited, rerun automatically by `build-custom-dataset.js`; see "Types of Christ pipeline" in `docs/treemap-and-datasets.md`), all sharing one `{name, references: {BOOKID: [{verse, subtopics, refs}]}, books}` schema: **Nave's Topics** (`topics`), **BSB Topics** (`bsb-topics`), **Prophecy** (`prophecy`, has its own aggregate-topic logic via `PROPHECY_AGGREGATE_TOPICS`), **BSB Concordance** (`concordance`, word-level references with a stopword filter), and **Custom Dataset** (`custom`, hand-maintained via `source/custom-topics.json` + `scripts/build-custom-dataset.js`; ref lines take `Ref | note` or `Ref | theme | note`, where a theme is a short label repeated verbatim across verses so the subtopic dropdown can group them - one-verse groups are hidden for this dataset via `SUBTOPIC_FILTER_MIN_PASSAGES`, since every per-verse note is otherwise its own useless group). `allTopicNames` (`Object.keys(topicsData)`) is each dataset's topic list in its JSON file's key order — reused as-is by the random-topic button, the suggestion dropdown, and the Previous/Next topic buttons (see below); reordering a dataset's source JSON changes all three. `switchDataset()` (extracted from the `#dataset-mode` `<select>`'s `change` handler) runs on every dataset switch and tries to carry the current search term over: an exact case-insensitive match in the new dataset first, then the same startsWith/contains matcher `getTopicOptions()` uses for suggestions, and only then that dataset's `defaultTopic` via `getDatasetDefaultTopic()` - the fuzzy step is skipped when the carried term is empty, since `getTopicOptions("")` returns the blank-query default list and its first entry would otherwise beat `defaultTopic` (Prophecy landed on "1. Seed of a woman" instead of its aggregate whenever the field was blank at switch time). See `docs/treemap-and-datasets.md` for dataset schemas, source files, and parser scripts.
- The search field (`#topic-input`) has a circular `&times;` clear button (`#topic-clear-btn`, inside `.topic-input-wrap`) instead of a separate "Reset Topic" button. Clicking it always clears the field to no topic (`applyTopicSelection(null, { commit: true })`), in every state. `updateTopicActionState()` hides it whenever `selectedTopic` is null (nothing to clear); while a topic is selected it is always visible (it used to appear only on hover/focus, which hid the fact that an auto-chosen topic like Prophecy's default aggregate could be cleared at all). **Focusing the field selects its whole value** (address-bar convention, with a one-shot `mouseup` preventDefault so the click that focused it doesn't collapse the selection) and opens the **blank-query** suggestion list rather than the matches for the current topic's own name - the next keystroke replaces the topic, so the user never has to find the × first. A click on an already-focused field (no focus event) reopens the list filtered by the current text. The placeholder carries the dataset's size (`getTopicInputPlaceholder()`, "Search 4,644 topics", via each `DATASET_CONFIG` entry's `countNoun`; Prophecy's count excludes its synthetic aggregates via `getTopicCatalogCount()`), refreshed by `updateDatasetUI()` at the end of `loadTopics()` once the count is known, and the blank-query list opens with a sticky `.topic-suggestions-caption` row (`getTopicSuggestionsCaption()`: "Top 50 of 4,644 topics by references. Type to search all." / "All 351 prophecies, in source order. Type to search."). Both exist because the search field is the narrowest portal to the data and the popularity-sorted default list otherwise reads as if those 50 were everything. Autocomplete is **not** a native `<datalist>` — it's a custom-built `#topic-suggestions` listbox (`renderTopicSuggestions()` etc.), built because native datalist popups are unreliable on mobile. Pressing Enter with the suggestions list open and a non-empty search term selects the highlighted suggestion, or the top one if none is highlighted (matches the usual search-box convention — the common case used to require arrowing down to the first result before Enter would do anything); an **empty** field still falls through to the commit/clear branch instead, so clearing the field and pressing Enter clears the topic rather than re-selecting whatever's first in the blank-query list. `getTopicOptions()`'s blank-query branch normally returns `allTopicNames.slice(0, maxOptions)` (alphabetical/natural order, since `allTopicNames` is also what Prev/Next-topic and the random-topic button step through and reordering it would change those too) — Nave's Topics, BSB Topics, People, Places, and BSB Concordance (`defaultSuggestionsBy: "popularity"` in their `DATASET_CONFIG` entries) instead get a separate `popularTopicNames` list, sorted by total verse-reference count and computed once per `loadTopics()` call, capped at `DEFAULT_POPULAR_SUGGESTION_COUNT` (50): an alphabetical blank-query default was mostly obscure entries starting with "A" (worst for People/Places, with ~1,870/~1,158 entries each), where a "most mentioned/referenced" list is a far more useful, attention-grabbing thing to show before the user's typed anything. Prophecy and Custom Dataset are deliberately left out: Prophecy's entries are already numbered in the source doc's own order (1, 2, 3, ... 351 - see its `maxOptions: 400` comment), which reads more naturally as a blank-query default than a popularity re-sort, and would also need its synthetic `"[All] OT/NT/Combined"` aggregate topics (see `withProphecyAggregateTopics`) excluded from the ranking first, since each one combines every specific prophecy's references and would otherwise bury the real ones. Custom Dataset is hand-curated and small, so "popularity" isn't a meaningful signal for it the way it is for the sourced datasets.
- `.topic-search-label-row` also holds four nav buttons after the 🎲 random button: Back/Forward (`#topic-back-btn`/`#topic-forward-btn`) are plain `history.back()`/`history.forward()` shortcuts — every committed topic/subtopic/dataset change pushes a real browser-history entry (see below), so these buttons, the browser's own Back/Forward, and a mouse's side buttons all retrace the exact same timeline. `updateTopicNavButtonState()` approximates their disabled state from `historySeqCounter`/`currentHistorySeq` (a push-sequence-number counter tagged onto each entry's `history.state`, since browsers don't expose "how many entries back/forward exist" to a page) — accurate within the current page load, not across a refresh. Previous/Next (`#topic-prev-btn`/`#topic-next-btn`) are unrelated — they step through `allTopicNames` in-place rather than any history. All four disable at their respective boundaries via `updateTopicActionState()`.
- Deep links: `?dataset=<mode>&topic=<name>&subtopic=<label>` in the URL overrides `localStorage` on boot, and `syncHistory()` keeps the URL in sync — `history.pushState` for a real committed action (topic/subtopic/dataset change, or state/book/chapter/verse navigation; `applyTopicSelection`'s `commit || isExactMatch` check decides if a topic edit counts), `history.replaceState` for in-chapter verse hops and for history restores themselves (`isRestoringHistory`-guarded, so a popstate-triggered re-render can't push its own entry). `popstate` (real Back/Forward, or a mouse's side buttons) restores the full position — topic/subtopic/dataset via `applyUrlTopicState()`, state/book/chapter/verse via `applyUrlNavState()` — from whatever URL the browser just navigated to.

## Overview treemap sizing (js/app.js)
- Each book card's height is proportional to its character count (`data/book-character-counts.json`), via `enforceAspectRatios()` (~line 1209): a `value^0.3` weight compresses the ~138x size range to ~4.4x, then items are greedily packed into 14 columns (canonical Genesis→Revelation order) with a binary-searched unit scale so columns absorb however many books fit, with each column's fill stretch capped at `MAX_COLUMN_FILL_FACTOR = 1.3` (keeps Revelation from being stretched larger than Matthew in the sparse last column). `scripts/verify-treemap-packing.js` re-runs this against real data outside the browser. Full algorithm and rationale in `docs/treemap-and-datasets.md`.

## Pin-line bands (js/app.js)
- Topic/word references inside each book/chapter card render as `.pin-line` elements grouped into `PIN_LINE_BANDS = 8` vertical `.pin-line-band` rows (`getPinLineBandIndex()`, ~line 290), based on each reference's position (0-100%) within the book/chapter. A reference near the end of a book renders near the bottom of the card; empty bands render as blank space. Used in both the Bible state (`renderTreemap`, book cards) and Book state (`renderBookView`, chapter cards) — same recipe, mirrored. Neither the Chapter state (`renderReadView`, single-chapter text reading view) nor the Verses state (`renderVersesView`, flat cross-book verse list) uses pin-lines. Full details in `docs/treemap-and-datasets.md`.

## Install as an app (js/app.js, site.webmanifest)
- Same recipe as Bible Peruser's `window.bpInstall`. `window.beInstall` (`canPrompt()`, `prompt()`, `isStandalone()`) is the first thing in `js/app.js` so its `beforeinstallprompt` listener is registered as early as possible; it keeps the event and dispatches `be-install-change` on `document` (also on `appinstalled`). On Android it returns without `preventDefault()` - Chrome's own install banner works well there and would be suppressed. No service worker, on purpose: installed still means online.
- `showAboutModal()` shows an "Install as an app" button (`.about-install-btn`) only while `canPrompt()` is true, re-synced on `be-install-change` - never a dead button. Non-Chromium browsers that aren't already standalone get one note instead ("can be installed as an app from Chrome or Edge"); Chromium gets nothing extra, since a missing button there almost always means it's already installed. On iPhone/iPad (every browser there is WebKit, and iPadOS reports as a Mac so it is detected by touch points) that note instead reads "To install on this iPhone: tap Share, then Add to Home Screen." - kept in the About modal rather than a first-visit popup, since this app has no first-visit tip and an unprompted modal is more intrusive than the hint is worth.

## Responsive breakpoints (css/style.css)
- `max-width: 899.98px`: real mobile layout (not an overlay — `#app` reflows into a normal scrolling column). The `.mini-state-switcher` buttons replace the slider, `.reading-sidebar` panels are hidden (see below), and `.header-right` collapses into the hamburger menu (`#menu-toggle`).
- `max-width: 780px`: tablet tweaks, layered on top of the 899.98px block above.
- `max-width: 1400px`: `.reading-sidebar` (Chapter/Verses states) is hidden — a narrower-desktop breakpoint, well above the 900px mobile cutoff.
- `min-width: 1101px and max-width: 1920px`: HD — tighter spacing/sizes for header controls.
- `min-width: 2560px`: 4K — larger fonts/padding throughout (lots of breathing room).

## Metadata (index.html head, site.webmanifest, robots.txt, netlify.toml)
- Hosted on Netlify (live response headers say `Server: Netlify`); push-to-`main` deploys. `index.html`'s head carries a meta description, Open Graph / Twitter card tags, canonical URL (`https://bible-explorer.gospelgo.org/` — the old head pointed `og:url` at a nonexistent `bibleexplorer.` host), theme-color (`#0b0e14` = `--ink-1`), `site.webmanifest` (installable, `display: standalone`) and a schema.org `WebApplication` JSON-LD block typed `ReferenceApplication`. Same recipe as Bible Peruser (2026-11-09), and for the same reason beyond search/link previews: some corporate web filters block the whole gospelgo.org domain family as "Games" (the parent site hosts Bible games), and vendor crawlers rate a subdomain separately only when its own content tells them what it is — keep the wording about Bible study by topic. Lead with "Bible study", not the translation: the Berean Standard Bible is named only at the end of the long descriptions and left out of the short ones.
- `robots.txt` is a plain allow-all (no signed-in pages here, unlike Peruser). `netlify.toml` exists only for `Cache-Control: public, max-age=604800, must-revalidate` on the full Bible text and the six sourced datasets, which otherwise get Netlify's default `max-age=0, must-revalidate` and a conditional request on every tab open; `data/custom-topics-with-references.json` is deliberately left at the default because it's the one dataset under active editing. A reparsed dataset can take up to a week to reach a returning visitor — accepted trade-off, same as Peruser.
- `document.title` is set per position by `updateDocumentTitle()` in `js/app.js`, called at the top of `syncHistory()` so every committed change, popstate restore and deep-link boot gets it: "LOVE · Genesis 3 — Bible Explorer" (topic[: subtopic], then Book / "Book N" / "Verses"), plain "Bible Explorer" on the bare Overview.
- Images: `images/favicon-explorer-v3.png` (512×512) is the app icon everywhere — tab favicon, `shortcut icon`, `apple-touch-icon` and manifest icon. `scripts/generate-share-images.js` (Node built-ins only, copied from Peruser with this app's icon/output/background swapped in) derives `images/bible-explorer-card-1200x630.png` from it plus `images/gospelgo-logo.png`, the `og:image` / `twitter:image` card: app icon left, Gospel Go wordmark right (at its native 620×300, never enlarged), on `--ink-1`. Rerun it after `generate-favicon-v3.js` if the icon ever changes. The shared brand-art folder's `BibleExplorer.png` (`C:\Unity Projects\_Art\GospelGoBrand\`) is **not** this app's icon.
